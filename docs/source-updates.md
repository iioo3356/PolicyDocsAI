# 소스로 정책 업데이트하기

[문서 목록](README.md) · [정책 채팅](policy-chat.md)

## 사용자 흐름

1. 채팅의 관련 소스 업데이트 버튼 또는 소스 추가 패널을 연다.
2. 업데이트할 기존 소스를 선택하고 같은 형식의 최신 파일을 올린다.
3. 분석 완료 후 정책 관리에서 업데이트 후보를 연다.
4. 연결된 기존 정책, 변경 전·후의 제목·요약·분류·규칙과 새 소스 근거를 비교한다.
5. **변경 승인**을 누르면 같은 정책 ID에 반영되고 Docs의 수정 이력에 기록된다.

재업로드·분석만으로 정책을 바꾸지 않는다. 반려·분석 실패 시 기존 정책을 유지한다.
자동 연결이 없는 후보는 관련 기존 정책을 직접 선택하거나 새 정책으로 승인할 수 있다.
자동 연결은 제안이며 최종 반영은 사람이 확인한다.
후보 하나의 전체 내용으로 대상 정책의 제목·요약·분류·규칙을 교체하므로,
여러 소스의 규칙을 합친 정책은 유지할 규칙까지 검토 화면에서 확인해야 한다.

## API와 저장

- `POST /projects/{project_id}/sources` multipart에 선택적으로 replaces_source_id를 전달한다.
- 기존 소스는 같은 프로젝트, 분석 COMPLETED, 동일 파일 형식이어야 한다. 기존 역할을 계승한다.
- 새 Source와 SourceVersion을 만들고 이전 소스 ID와 업로드 시점의 연결 정책 내용·updated_at을 보관한다.
- 파일·근거를 덮어쓰지 않는다. 동일 바이트와 파일명일 때 저장 파일 자체는 공유할 수 있다.
- 새 테이블 source_versions는 시작 시 create_all로 생성한다. 기존 테이블의 컬럼 변경은 없다.
- 후보 승인 요청의 target_policy_id 또는 proposed_policy_id로 수정할 기존 정책을 결정한다.
- `GET /policies/{policy_id}/revisions`는 최신순으로 수정 이력을 반환한다.
- 직접 `PATCH /policies/{policy_id}`는 409로 소스 업데이트 절차를 안내한다.

## 연결과 일관성

- 이전 소스의 근거와 새 chunk의 문서 위치·심볼 또는 동일 내용이 일치하고 대상이 하나일 때만 정책 ID를 제안한다.
- 코드 ZIP은 파일 경로도 같아야 한다. 제목 변경·파일 이동·모호한 연결은 자동 연결되지 않을 수 있다.
- 문서의 행이나 제목 위치가 재사용되면 다른 내용을 제안할 수 있으므로 반드시 변경 전후를 검토한다.
- 승인 직전 후보와 정책을 잠그고 프로젝트·승인 상태·이전 소스 연결을 확인한다.
- 업로드 시점과 정책 내용·updated_at이 다르면 409다. 최신 소스를 다시 올려 검토해야 한다.
- 정책·전체 규칙·search_text·새 근거·후보 승인 상태·수정 이력을 한 트랜잭션으로 저장한다.
- 이력은 변경 전후와 소스 ID, 이전 소스 ID, 후보 ID, chunk ID, 파일명·경로를 보관한다.
- 과거 근거도 보존하며 Docs에서 이전 버전으로 표시한다. 채팅 근거는 최신 수정의 chunk를 사용한다.
- 근거 또는 후속 소스 버전이 참조하는 소스는 삭제할 수 없다.
- 승인된 후보의 재승인·반려는 409다. 저장 실패 시 변경과 이력을 함께 rollback한다.

## 현재 범위

파일 전체를 비교해 사라진 정책을 자동 폐기하거나 여러 후보를 일괄 병합하지 않는다.
한 정책에 연결된 후보를 여러 개 승인하려면 먼저 승인된 변경 때문에 나머지가 오래된 상태가 될 수 있다.
필요한 전체 규칙을 한 변경안에서 검토하거나 최신 소스로 다시 분석한다.
기존 후보 병합 API는 유지하며, 소스 업데이트 후보의 경우 연결 정책을 갱신하는 흐름으로 처리한다.
SQLite 회귀 테스트는 트랜잭션·상태를 검증하지만 PostgreSQL 동시 잠금 동작의 부하 검증을 대신하지 않는다.
